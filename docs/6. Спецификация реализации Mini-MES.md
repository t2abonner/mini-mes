## 1. Назначение документа

Настоящий документ определяет архитектурные и технические решения, необходимые для реализации учебного проекта Mini-MES.

Документ предназначен для разработчика учебного проекта и техлида/ментора, осуществляющего код-ревью.

Документ отвечает на вопрос: как именно команда из двух участников (разработчик и техлид) реализует учебный проект, воспроизводящий технологический стек и ключевые механизмы реального проекта MES-MF в сокращённом масштабе.

В случае противоречия между настоящим документом и документами 1–3 приоритет имеет настоящий документ: документы 1–3 являются «входящей» справочной документацией и применяются только в части, явно заимствованной настоящим документом.

## 3. Границы системы

### 3.1. Зона ответственности Mini-MES

Система отвечает за:
- аутентификацию пользователей и разграничение доступа по ролям (RBAC, сокращённый набор);
- аналитический дашборд только для чтения с обновлением в реальном времени;
- карточку задания оператора со стартом и завершением операции;
- фиксацию брака;
- складские перемещения в объёме просмотра списка и подтверждения выполнения;
- уведомления пользователя;
- офлайн-очередь цеховых операций с последующей синхронизацией;
- светлую и тёмную темы оформления.

### 3.2. Вне зоны ответственности Mini-MES

Система не реализует:
- интеграции с 1С:КА, amoCRM и САПР «Базис-Мебельщик»;
- модуль конструкторской документации и карантин файлов;
- учёт рабочих смен и экспорт отработанных часов;
- административный модуль (пользователи, роли, настройки);
- фоновые воркеры, базу данных PostgreSQL, кэш Redis, контейнеризацию Docker;
- прогнозирование сроков на основе истории скоростей (прогноз задаётся мок-сервером напрямую).

### 3.3. Роль мок-сервера

Работу backend-разработчиков реального проекта в учебном контуре выполняет мок-сервер `apps/mock-api`. Клиентское приложение разрабатывается исключительно против контракта настоящего документа и не использует знаний о реализации мок-сервера.

## 8. Серверная часть (мок-сервер)

### 8.1. Тип серверного приложения

Мок-сервер реализуется как однопроцессное приложение Node.js (Express + Socket.IO). Данные хранятся в массивах в оперативной памяти; перезапуск процесса возвращает систему в исходное состояние стенда.

### 8.2. Коллекции данных

`users`, `orders`, `batches`, `machines`, `shopTasks`, `movements`, `defects`, `notifications`, а также служебные `sessions` и `idempotencyStore`.

### 8.3. Аутентификация

- Вход: `POST /api/v1/auth/login` по логину и паролю; при неверных данных — 401 с кодом `AUTH_INVALID_CREDENTIALS`.
- Токены — непрозрачные случайные строки; access-токен живёт 120 секунд для тренировки механики 401 → refresh → повтор запроса.
- `POST /api/v1/auth/refresh` выпускает новый access-токен по действительному refresh-токену.
- `GET /api/v1/auth/me` возвращает текущего пользователя и роль.
- `POST /api/v1/auth/logout` отзывает сессию.

### 8.4. Идемпотентность

- Для изменяющих операций клиент передаёт заголовок `Idempotency-Key`.
- Сервер хранит обработанные ключи в `idempotencyStore` вместе с хэшем запроса и ответом.
- Повторный запрос с тем же ключом и тем же телом возвращает сохранённый ответ без повторного изменения данных.
- Повторный запрос с тем же ключом и иным телом отклоняется с кодом `IDEMPOTENCY_CONFLICT` (409).

### 8.5. Формат ошибки и типовые коды

Формат ошибки копирует §15.3 спецификации MES-MF:

```json
{
  "timestamp": "2026-09-03T10:00:00Z",
  "errorCode": "TASK_ALREADY_COMPLETED",
  "message": "Задание уже завершено."
}
```

| Код | Описание |
| --- | --- |
| AUTH_INVALID_CREDENTIALS | Неверный логин или пароль |
| AUTH_TOKEN_EXPIRED | Токен истек |
| FORBIDDEN | Недостаточно прав |
| VALIDATION_ERROR | Ошибка валидации |
| NOT_FOUND | Ресурс не найден |
| CONFLICT | Конфликт состояния |
| TASK_ALREADY_COMPLETED | Задание уже завершено |
| MOVEMENT_ALREADY_COMPLETED | Перемещение уже завершено |
| IDEMPOTENCY_CONFLICT | Конфликт идемпотентности |

### 8.6. Симулятор цеха

Таймер с периодом ~10 секунд выполняет один из сценариев и рассылает события Socket.IO:
1. Приращение годных деталей по выполняющемуся заданию (1–5 шт.) с пересчётом прогресса заказа — `dashboard.order.updated`, `dashboard.summary.updated`.
2. Изменение статуса случайного станка (`running` ↔ `idle` / `maintenance`) — `dashboard.machine.updated`.
3. Фиксация брака с вероятностью ~15% — `dashboard.defect.created` и `notification.created`.

## 12. Бизнес-правила учебного контура

12.1. Прогресс заказа: `progressPercent = goodQty / totalPlannedQty * 100`, ограничивается 100.

12.2. Процент брака: `defectPercent = defectQty / totalPlannedQty * 100`, отображение с одним знаком.

12.3. Индикатор отклонения: `delay = predictedFinishAt − plannedFinishAt`. Уровни:

| Уровень | Условие |
| --- | --- |
| neutral | прогноз не превышает план |
| warning | превышение не более 60 минут |
| critical | превышение более 60 минут |

Пороги в учебном контуре фиксированы (60 минут) и хранятся в конфигурации мок-сервера.

12.4. Заказ считается выполненным при `goodQty >= totalPlannedQty` и завершении всех партий.

12.5. Брак не уменьшает требуемое количество годных деталей.

12.6. Завершение уже завершённого задания отклоняется с кодом `TASK_ALREADY_COMPLETED`; завершение уже завершённого перемещения — с кодом `MOVEMENT_ALREADY_COMPLETED`.

## 13. Спецификация REST API

### 13.1. Общие требования

## 15. Клиентское приложение

### 15.1. Общие требования

Приложение реализуется как SPA на React 18 + TypeScript; интерфейс на русском языке; светлая и тёмная темы; целевой экран 1920×1080; дашборд обновляется без ручной перезагрузки.

### 15.2. Структура `apps/web`

```
apps/web/src/
 ├── app/            # providers, router, styles, App.tsx
 ├── pages/          # login, dashboard, shop-task, warehouse, forbidden
 ├── widgets/        # layout, header, sidebar, dashboard-summary,
 │                   # orders-table, machines-panel, order-timeline, notifications
 ├── features/       # auth, theme, complete-operation, report-defect,
 │                   # offline, notifications
 ├── entities/       # user, order, machine, shop-task, movement
 └── shared/         # api, config, hooks, lib, ui
```

Правило зависимостей: `pages → widgets → features → entities → shared`; `shared/ui` реэкспортирует компоненты `packages/ui`.

### 15.3. Роутинг

| Путь | Назначение | Доступ |
| --- | --- | --- |
| /login | Вход | публичный |
| /dashboard | Дашборд | dashboard.read |
| /shop/tasks/:id | Операция | shop.operate |
| /warehouse | Склад | warehouse.execute |
| /forbidden | Недостаточно прав | авторизованные |

Неавторизованный пользователь перенаправляется на `/login` с сохранением исходного пути; авторизованный пользователь без права — на `/forbidden`.

### 15.4. Управление состоянием

| Тип состояния | Технология |
| --- | --- |
| Серверные данные | TanStack Query |
| Клиентское состояние (тема, сессия, статус связи, офлайн-статус) | Zustand |
| Локальное состояние форм | React Hook Form |
| Фильтры/сортировки дашборда | React Router searchParams |
| Real-time | Socket.IO + инвалидация TanStack Query |

### 15.5. Работа с API (Axios)

- Единый инстанс с базовым URL из конфигурации окружения.
- Интерцептор запроса добавляет `Authorization: Bearer`.
- Интерцептор ответа: при 401 выполняет однократное обновление токена и повторяет исходный запрос; при 403 формирует сообщение о недостатке прав; при 409 передаёт конфликт состояния в интерфейс; нормализует ошибку к виду `{ errorCode, message }`.

### 15.6. Ключи запросов и инвалидация

| QueryKey | Источник | Инвалидируется событиями |
| --- | --- | --- |
| ['dashboard','summary'] | GET /dashboard/summary | summary.updated, order.updated, defect.created, snapshot |
| ['dashboard','orders', filters] | GET /dashboard/orders | order.updated, defect.created, snapshot |
| ['dashboard','machines'] | GET /dashboard/machines | machine.updated, snapshot |
| ['order','timeline', id] | GET /orders/{id}/timeline | по требованию (открытие диалога) |
| ['shop','task', id] | GET /shop/tasks | после мутаций и конфликтов |
| ['warehouse','movements'] | GET /warehouse/movements | после мутаций |
| ['notifications'] | GET /notifications | notification.created |

### 15.7. Работа с Socket.IO

Клиент подключается после авторизации и отключается при выходе. Автоматическое переподключение обеспечивается клиентом Socket.IO; после переподключения сервер присылает `dashboard.initial.snapshot`. Статус соединения отображается индикатором в шапке (значение из Zustand).

### 15.8. Формы и валидация

Формы реализуются на React Hook Form с резолвером Zod; схемы размещаются в `packages/validation`; сообщения валидации — только на русском языке. Формы учебного контура: логин; завершение операции (goodQuantity, defectQuantity, defectReason); фиксация брака (quantity, reason).

### 15.9. Стилизация и темы

CSS Modules + CSS-переменные; набор токенов и значения светлой/тёмной темы заимствуются из §18.9 спецификации MES-MF без изменений; переключение через `<html data-theme="dark">`; выбранная тема сохраняется в localStorage и восстанавливается при загрузке.

### 15.10. UI-кит (`packages/ui`)

Компоненты: `Button`, `Input`, `Textarea`, `Select`, `Card`, `Badge`, `Dialog`, `Tabs`, `Toast`, `Loader`, `EmptyState`, `ErrorState`. Примитивы доступности (Select, Dialog, Tabs, Toast) — Radix UI. Документирование — Storybook. Иконки — lucide-react.

### 15.11. Дашборд

Блоки: сводная статистика (8 показателей §19.3 спецификации MES-MF); таблица заказов (TanStack Table) с полями карточки заказа (§19.4 в сокращении: номер, клиент, статус, план/прогноз, индикатор отклонения, прогресс, брак шт/%, текущая зона, партия N из M, плиты/кромка/отверстия); панель станков с группировкой по зонам (§19.6 спецификации MES-MF); таймлайн заказа в `Dialog` (§4.1.7.10 ТЗ).

Фильтры: статус, зона, клиент, наличие отклонения. Сортировка: плановая дата, прогресс, уровень отклонения, уровень брака. Фильтры и сортировка хранятся в searchParams и переживают перезагрузку страницы.

Для каждого блока обязательны состояния Loading, Error (с кнопкой повтора) и Empty. Страницы загружаются лениво (`React.lazy` + `Suspense`).

Расчёты на клиенте: индикатор отклонения и форматирование дат — date-fns (`differenceInMinutes`, `format`, `formatDistanceToNow`).

### 15.12. Цеховой терминал

Карточка задания (`/shop/tasks/:id`): данные задания, станок, план/факт; действия «Начать операцию» и «Завершить операцию» (форма RHF+Zod, мутация с `Idempotency-Key`); форма фиксации брака. Мутации используют оптимистичное обновление с откатом при ошибке.

### 15.13. Склад

Список перемещений с текущими статусами; действие «Подтвердить выполнение» для перемещений в статусах `assigned`/`in_progress`; повторное подтверждение обрабатывает 409 `MOVEMENT_ALREADY_COMPLETED` обновлением списка.

### 15.14. Уведомления

«Колокольчик» в шапке: список уведомлений текущего пользователя, счётчик непрочитанных; событие `notification.created` инвалидирует `['notifications']`.

## 16. Офлайн-режим цехового терминала

16.1. Поддерживается офлайн: просмотр текущего задания (из кэша TanStack Query); отметка начала операции; отметка завершения операции; фиксация брака.

16.2. Не поддерживается офлайн: склад, дашборд-мутации не существуют по построению (дашборд read-only), администрирование.

16.3. Механизм: операции сохраняются в IndexedDB (Dexie) в таблицу `offlineQueue` со схемой `{ ++id, idempotencyKey, method, url, payload, createdAt, status }`, статусы: `pending`, `synced`, `conflict`.

16.4. Определение связи: события `online`/`offline` браузера плюс периодический пинг `GET /health`; статус связи хранится в Zustand и отображается баннером терминала.

16.5. Синхронизация: при восстановлении связи операции отправляются последовательно в порядке `createdAt` с тем же `idempotencyKey`; успех — запись удаляется из очереди; 409 (`TASK_ALREADY_COMPLETED`) — запись помечается `conflict`, интерфейс показывает актуальное состояние задания (рефетч); 401 — обновление токена и продолжение.

## 17. Безопасность учебного контура

17.1. Пароли в мок-сервере хранятся открыто; это осознанное упрощение стенда, явно не переносимое в реальную систему.

17.2. Проверка прав выполняется мок-сервером на каждом защищённом эндпоинте; интерфейс скрывает недоступные действия, но не подменяет серверную проверку.

17.3. Дашборд не предоставляет мутаций.
