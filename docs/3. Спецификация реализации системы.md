## 1. Назначение документа

Настоящий документ определяет архитектурные и технические решения, необходимые для реализации системы MES-MF в соответствии с техническим заданием и согласованными проектными решениями.

Документ предназначен для:

- backend-разработчиков;
- frontend-разработчиков;
- QA-инженера;
- системного аналитика;
- менеджера проекта;
- специалистов, участвующих в интеграции с 1С:Комплексная автоматизация;
- специалистов, участвующих в настройке обмена с САПР «Базис-Мебельщик»;
- администраторов системы.

Документ отвечает на вопрос:

> как именно команда реализует требования, описанные в техническом задании.

В случае противоречия между настоящим документом и техническим заданием приоритет имеет техническое задание, а выявленное противоречие должно быть вынесено на обсуждение системному аналитику и менеджеру проекта.

## 3. Границы системы

### 3.1. Зона ответственности MES-MF

Система отвечает за:

- прием производственных заказов из 1С:КА;
- управление конструкторской документацией;
- создание партий мастером смены;
- формирование сменных заданий;
- учет перемещений материалов, полуфабрикатов и готовых деталей;
- фиксацию операций, брака и простоев;
- фиксацию начала, прерывания и окончания рабочих смен пользователей;
- формирование отчета по фактически отработанным часам и его экспорт в 1С;
- передачу фактов производства обратно в 1С:КА;
- аналитический дашборд в реальном времени;
- фиксацию дефицита материалов;
- уведомления о проблемах с КД, интеграциями, поступлением материалов и лимитами рабочих смен.

### 3.2. Вне зоны ответственности системы

Система не отвечает за:

- продажи и коммуникацию с клиентами;
- бухгалтерский учет;
- расчет стоимости заказов;
- закупки материалов;
- сделки с поставщиками;
- количественно-суммовой складской учет;
- формирование прайс-листов;
- выставление счетов;
- расчет заработной платы;
- кадровый учет;
- учет остатков обрезков плит.

### 3.3. Прямая интеграция с amoCRM

Прямая интеграция с amoCRM в рамках текущего проекта не выполняется.

Система только сохраняет идентификатор сделки в amoCRM, полученный из 1С:КА, для сквозной трассировки заказа.

## 4. Принятые архитектурные решения

| Номер | Решение | Обоснование |
|---|---|---|
| ADR-01 | Использовать модульный монолит вместо микросервисов | Соответствует масштабу проекта и снижает операционную сложность |
| ADR-02 | Единый язык TypeScript для frontend и backend | Упрощает разработку, позволяет переиспользовать типы и контракты |
| ADR-03 | Backend на Node.js LTS + NestJS | Модульная архитектура, удобная для RBAC, API, WebSocket |
| ADR-04 | ORM Prisma | Удобная работа с PostgreSQL, миграции, типобезопасность |
| ADR-05 | Real-time через Socket.IO | Устойчивость, автоматическое переподключение, удобная событийная модель |
| ADR-06 | Монорепозиторий на npm workspaces без Turborepo | Достаточно для текущего размера проекта и упрощает инфраструктуру |
| ADR-07 | Frontend на React 18 + TypeScript | Согласованный командой стек |
| ADR-08 | Стилизация через CSS Modules и CSS-переменные вместо Tailwind | Требование команды, более контролируемая стилизация |
| ADR-09 | HTTP-клиент Axios | Согласовано командой |
| ADR-10 | Использовать Storybook для разработки и документации UI-компонентов | Удобство разработки изолированных компонентов |
| ADR-11 | Интеграция с 1С:КА по гибридной схеме: OData + HTTP-сервисы + периодический обмен | OData и HTTP-сервисы доступны, требуется надежный обмен не реже 15 минут |
| ADR-12 | Не выполнять прямую интеграцию с amoCRM | MES получает заказы из 1С; прямая интеграция с amoCRM вне текущего объема |
| ADR-13 | Использовать Outbox/Inbox для интеграций | Надежная доставка и идемпотентная обработка событий |
| ADR-14 | Дашборд строится на отдельной read-model | Повышает скорость загрузки и обновления дашборда |
| ADR-15 | Терминалы цеха поддерживают офлайн-очередь операций | Требование устойчивости к потере связи |
| ADR-16 | Партии создаются только мастером смены вручную | Автоматическое разделение заказа на партии не выполняется |
| ADR-17 | Брак требует производства замены | Заказ не считается выполненным, пока не произведено полное количество годных деталей |
| ADR-18 | MES фиксирует распределение материалов и дефицит, но закупка остается в 1С | Разделение ответственности между MES и 1С |
| ADR-19 | Добавляется модуль учета фактически отработанных часов | Требуется экспорт часов в 1С для расчета заработной платы |
| ADR-20 | В системе могут быть несколько администраторов | Коммерческий директор получает администратора при инициализации, также создается технический администратор |
| ADR-21 | Интеграция с 1С реализуется через конфигурируемые маппинги | Имена объектов и полей 1С уточняются в процессе интеграции без изменения базовой архитектуры |
| ADR-22 | Неиспользуемые остатки плит не учитываются | Остаток плиты считается потенциальным мусором и не подлежит складскому учету |

## 6. Структура монорепозитория

Используется монорепозиторий на базе **npm workspaces**.

Turborepo не используется.

### 6.1. Корневая структура

```text
/
├── apps/
│   ├── api/                    # NestJS API
│   ├── worker/                 # Фоновые воркеры
│   └── web/                    # React SPA
├── packages/
│   ├── contracts/              # OpenAPI, DTO, типы событий
│   ├── validation/             # Общие схемы валидации
│   ├── ui/                     # UI-библиотека и Storybook
│   ├── eslint-config/          # Общие настройки ESLint
│   └── tsconfig/               # Общие настройки TypeScript
├── docker/
├── docs/
├── scripts/
├── package.json
└── package-lock.json
```

### 6.2. Корневой `package.json`

```json
{
  "name": "mes-mf",
  "private": true,
  "workspaces": [
    "apps/*",
    "packages/*"
  ],
  "scripts": {
    "dev": "npm run dev:api & npm run dev:worker & npm run dev:web",
    "dev:api": "npm run dev --workspace=apps/api",
    "dev:worker": "npm run dev --workspace=apps/worker",
    "dev:web": "npm run dev --workspace=apps/web",
    "build": "npm run build:packages && npm run build:apps",
    "build:packages": "npm run build --workspace=packages/contracts && npm run build --workspace=packages/validation && npm run build --workspace=packages/ui",
    "build:apps": "npm run build --workspace=apps/api && npm run build --workspace=apps/worker && npm run build --workspace=apps/web",
    "lint": "npm run lint --workspaces --if-present",
    "test": "npm run test --workspaces --if-present",
    "storybook": "npm run storybook --workspace=packages/ui",
    "build-storybook": "npm run build-storybook --workspace=packages/ui"
  }
}
```

### 8.3. Приложение воркеров

Отдельное приложение `apps/worker` отвечает за фоновые задачи.

Список воркеров:

1. `IntegrationInboxWorker`  
   Обрабатывает входящие сообщения из 1С.

2. `IntegrationOutboxWorker`  
   Отправляет исходящие события в 1С.

3. `FileIngestWorker`  
   Сканирует сетевую директорию Базис-Мебельщик.

4. `ForecastWorker`  
   Пересчитывает прогнозируемые сроки и уровни отклонений.

5. `DashboardSnapshotWorker`  
   Обновляет проекции для дашборда.

6. `WorkShiftWorker`  
   Отслеживает лимиты рабочих смен, отправляет предупреждения и автоматически закрывает смены.

7. `NotificationWorker`  
   Формирует уведомления для технологов, мастеров, кладовщиков и администраторов.

8. `RetentionWorker`  
   Удаляет или архивирует данные старше установленных сроков, если это требуется.

## 9. Ролевая модель и права доступа

### 9.1. Модель доступа

Используется RBAC:

```text
Пользователь -> Роли -> Права
```

Один пользователь может иметь несколько ролей.

Право — атомарная единица доступа.

### 9.2. Системные роли

| Роль | Код |
|---|---|
| Администратор системы | `admin` |
| Технический администратор | `technical_admin` |
| Коммерческий директор | `commercial_director` |
| Менеджер | `manager` |
| Старший технолог | `senior_technologist` |
| Технолог | `technologist` |
| Специалист снабжения | `supply_specialist` |
| Старший кладовщик | `senior_warehouse` |
| Кладовщик | `warehouse` |
| Мастер смены | `shop_master` |
| Оператор станка | `machine_operator` |

Роль `Бухгалтер` в системе не создается, так как бухгалтер не имеет доступа к системе.

Роль администратора по умолчанию назначается коммерческому директору при инициализации системы.

Дополнительно при развертывании или первом входе создается отдельный технический администратор.

Система поддерживает создание дополнительных администраторов.

### 9.3. Права доступа

- видеть дефицит материалов;
- формировать сменные задания;
- получать уведомления о поступлении материалов;
- просматривать собственные рабочие смены.

### 9.6. Дополнительные права оператора

Оператор станка имеет права:

- просматривать собственное задание;
- просматривать КД своего задания;
- начинать и завершать операцию;
- фиксировать брак;
- фиксировать простой;
- автоматически открывать рабочую смену при входе;
- прерывать смену по форс-мажорной причине;
- штатно завершать смену;
- просматривать собственные отработанные часы.

### 9.7. Администратор и технический администратор

Администратор имеет права:

- создавать пользователей;
- сбрасывать пароли;
- назначать роли;
- создавать роли;
- назначать права ролям;
- изменять настройки системы;
- просматривать интеграционные события;
- повторно отправлять интеграционные события;
- просматривать отчет по отработанным часам;
- корректировать рабочие смены при необходимости.

Технический администратор имеет тот же набор административных прав, если иное не ограничено отдельной ролью.

### 9.8. Правила управления пользователями и паролями

1. Пользователей создает только администратор.
2. Сброс паролей выполняет только администратор.
3. Самостоятельный сброс пароля пользователем не реализуется.
4. При сбросе пароля администратором пользователь обязан сменить временный пароль при первом входе.
5. Все административные действия фиксируются в аудите.

## 10. Модель данных

### 10.1. Общие требования к базе данных

- СУБД: PostgreSQL.
- Имена таблиц: `snake_case`.
- Первичные ключи: `UUID`.
- Внешние идентификаторы из внешних систем: строки, например `external_1c_id`.
- Даты и время: `TIMESTAMPTZ`, хранение в UTC.
- Денежные данные не хранятся.
- Цены и финансовые данные не передаются и не отображаются.
- Интеграционные сообщения хранятся в `JSONB`.
- Для истории статусов, простоев, аудита и рабочих смен предусматривается хранение не менее 12 месяцев.

## 12. Бизнес-правила

### 12.1. Прием заказа из 1С

При получении заказа со статусом «К производству» система:

1. Создает производственный заказ.
2. Проверяет обязательность всех полей заказа.
3. Сохраняет идентификатор заказа в 1С.
4. Сохраняет идентификатор сделки в amoCRM при наличии.
5. Сохраняет клиента.
6. Сохраняет перечень деталей.
7. Сохраняет плановые даты.
8. Устанавливает начальный статус `new`.
9. Формирует потребности в материалах.
10. Фиксирует событие в истории заказа.

Все поля заказа, передаваемого из 1С, являются обязательными.

Если обязательные поля отсутствуют:

- заказ не создается;
- входящее сообщение сохраняется в `integration_inbox` со статусом `validation_failed`;
- администратор видит ошибку в модуле интеграций;
- после исправления данных в 1С сообщение может быть обработано повторно.

### 12.2. Запуск заказа в производство

Заказ может быть переведен в статус `in_production`, если:

- заказ получен из 1С;
- пакет КД передан в цех;
- пользователь имеет право `orders.start` или `shop.manage`.

Запуск заказа в производство при частичном поступлении материалов разрешен.

При запуске система может показывать предупреждение:

```text
Материалы по заказу поступили частично. Доступно 8 из 12 плит.
```

Это предупреждение не блокирует запуск.

При запуске:

- проставляется `started_at`;
- создается событие истории;
- в 1С отправляется событие `ORDER_STATUS_CHANGED` со статусом `IN_PRODUCTION`.

### 12.3. Партии

Партии создаются только мастером смены вручную.

Автоматическое разделение заказа на партии не выполняется.

При создании партии мастер учитывает:

- общий объем заказа;
- текущую загрузку производства;
- доступный остаток материала на складе;
- приоритет заказа;
- плановые сроки.

Правила:

1. Партии создаются только пользователем с правом `batches.manage`.
2. Партии разных заказов могут обрабатываться параллельно.
3. Партии внутри одного заказа по умолчанию планируются последовательно, если мастер явно не организует параллельную обработку.
4. Заказ не считается выполненным, пока не завершены все партии заказа.
5. Каждая партия должна быть привязана к заказу и иметь уникальный номер в пределах заказа.

### 12.4. Распределение материалов

Мастер смены распределяет доступный остаток материала между заказами и партиями.

Источник данных об остатке — 1С:КА.

Если запрошенный объем не превышает доступный остаток:

```text
Статус распределения = allocated
```

Если запрошенный объем превышает доступный остаток:

```text
Статус распределения = deficit
```

При дефиците:

1. MES фиксирует дефицит.
2. Дефицит отображается в интерфейсе мастера и на дашборде.
3. Мастер смены, старший кладовщик и специалист снабжения видят проблемный заказ в блоке ожидающих материалов.
4. MES отправляет в 1С событие `MATERIAL_ALLOCATION_REQUESTED`.
5. 1С формирует потребность в закупке.
6. Специалист снабжения обрабатывает закупку в 1С.

Сама закупка и сделка с поставщиком в MES не выполняются.

### 12.5. Единицы измерения и округление материалов

#### 12.5.1. ЛДСП

| Параметр | Значение |
|---|---|
| Единица измерения | штуки плит |
| Код единицы | `sheet` |
| Правило округления | вверх до целой плиты |
| Учет остатков плит | не ведется |
| Остаток плиты | считается неиспользуемым и не учитывается |

Если расчет Базис-Мебельщик показывает дробную занятость плит, например 5.5 плит, потребность по заказу округляется до 6 плит.

Пример:

```text
Количество по данным Базиса: 5.5 плит
Количество для склада и производства: 6 плит
Остаток 0.5 плиты: не учитывается
```

Остаток плиты является потенциальным мусором и не подлежит складскому учету.

#### 12.5.2. Кромка

| Параметр | Значение |
|---|---|
| Единица измерения | погонные метры |
| Код единицы | `m` |
| Правило округления | вверх до целого метра |
| Дробные значения | не используются в складских перемещениях |

Пример:

```text
Количество по данным Базиса: 231.2 м
Количество для склада и производства: 232 м
```

### 12.6. Поступление материалов

Факт поступления материалов на склад фиксируется в 1С специалистом снабжения.

MES не вводит поступления материалов вручную.

Система получает данные о поступлении из 1С через:

- OData;
- событийное сообщение, если оно реализовано на стороне 1С.

После поступления материалов статус обеспечения заказа может измениться:

```text
waiting -> partial -> ready
```

### 12.7. Частичное поступление материалов

Частичное поступление материалов является штатным сценарием.

Система поддерживает следующий процесс:

1. Заказ получает статус «К производству».
2. Часть материала уже есть на складе, часть еще не поступила.
3. Мастер смены видит доступный остаток.
4. Мастер смены может запросить перемещение доступного материала в цех.
5. Кладовщик выполняет перемещение.
6. Позже поставщик доставляет недостающую часть.
7. 1С обновляет данные о поступлении.
8. MES получает обновленные данные.
9. Мастер смены получает уведомление о поступлении материала.
10. Мастер смены снова запрашивает перемещение материала в цех.
11. Цикл повторяется до полного обеспечения заказа.

При поступлении недостающей части материала уведомление получают:

- мастер смены;
- старший кладовщик;
- при необходимости специалист снабжения.

### 12.8. Учет брака

Брак:

- фиксируется оператором или мастером смены;
- указывается количество, зона, станок, причина;
- отображается в дашборде;
- передается в 1С;
- требует производства замены.

Брак не уменьшает требуемое количество годных деталей по заказу.

Если деталь забракована и для выполнения заказа требуется замена, система учитывает это как необходимость дополнительного производства.

Формальное правило:

```text
Требуемое количество годных деталей = total_planned_qty
Фактически годные детали = good_qty
Брак = defect_qty

Заказ выполнен, если:
  good_qty >= total_planned_qty
  и все партии завершены
  и готовые детали переданы на склад
```

Если брак фиксируется после того, как деталь была учтена как годная, система корректирует счетчики годных деталей и пересчитывает прогноз.

### 12.9. Прогресс заказа

Формула прогресса:

```text
progressPercent = goodQty / totalPlannedQty * 100
```

Где:

- `goodQty` — количество годных деталей, принятых как выполненные;
- `totalPlannedQty` — требуемое количество годных деталей по заказу.

Прогресс ограничивается значением 100.

### 12.10. Процент брака

Формула:

```text
defectPercent = defectQty / totalPlannedQty * 100
```

Допускается отображение с округлением до одного знака.

### 12.11. Прогнозируемый срок окончания

Прогноз рассчитывается на основании:

- оставшегося объема работ;
- текущей скорости обработки;
- истории операций;
- текущих простоев;
- состояния станков;
- необходимости производства замен бракованных деталей.

Базовая формула для первой реализации:

```text
remainingQty = totalPlannedQty - goodQty

if remainingQty < 0:
    remainingQty = 0

currentRate = средняя скорость производства за расчетный период
remainingHours = remainingQty / currentRate
predictedFinishAt = now + remainingHours
```

Для заказов с несколькими зонами допускается расчет по каждой зоне с последующим суммированием.

Прогноз пересчитывается:

- при завершении операции;
- при регистрации брака;
- при регистрации простоя;
- при перемещении партии;
- по расписанию, например каждые 5–15 минут.

### 12.12. Индикатор отклонения

Для каждого заказа рассчитывается:

```text
delay = predictedFinishAt - plannedFinishAt
```

Уровни:

| Уровень | Условие |
|---|---|
| Нейтральный | прогноз не превышает план |
| Предупреждающий | превышение не больше порога `deviation.warning_minutes` |
| Критический | превышение больше порога `deviation.critical_minutes` |

Пороги настраиваются администратором.

### 12.13. Отчетное окно смены для дашборда

Часовой пояс системы:

```text
Europe/Moscow
```

Начало отчетного окна смены:

```text
08:00
```

Максимальная длительность отчетного окна:

```text
12 часов
```

По умолчанию:

```text
Начало отчетного окна: 08:00 Москва
Окончание отчетного окна: 20:00 Москва
```

Если текущее время находится до начала отчетного окна, дашборд может отображать статистику за предыдущее отчетное окно.

Статистика «за текущую смену» рассчитывается по событиям, попавшим в текущее отчетное окно.

Индивидуальные рабочие смены пользователей учитываются отдельно в модуле `work_shifts`.

### 12.14. Правила учета рабочего времени

1. Минимальная базовая длительность смены оператора — 8 часов.
2. Максимальная длительность смены оператора — 12 часов.
3. Мастер смены работает 8 часов.
4. Смена открывается автоматически при входе пользователя в систему.
5. Мастеру смены не требуется вручную открывать или закрывать производственную смену.
6. Выход пользователя из системы штатно завершает смену.
7. Допускается форс-мажорное прерывание смены.
8. После прерывания смена может быть продолжена при повторном входе пользователя в рамках того же отчетного дня.
9. Перерывы внутри смены не вычитаются из отработанных часов.
10. После 8 часов оператор может продолжить работать сверхурочно по желанию.
11. По истечении 12 часов смена автоматически закрывается.
12. За 30, 20 и 10 минут до автозакрытия оператор получает уведомления.
13. Если смена завершается до 8 часов, система показывает предупреждение и помечает смену как требующую внимания.
14. Все ручные корректировки смен фиксируются в аудите.
15. Отчет по отработанным часам экспортируется в 1С для расчета заработной платы.

Формулы расчета:

```text
duration_minutes = ended_at - started_at
base_minutes = min(duration_minutes, 480)
overtime_minutes = max(duration_minutes - 480, 0)
```

Расчет заработной платы в MES не выполняется.

### 12.15. Автоматическое закрытие смены

Для каждой открытой смены система рассчитывает:

```text
auto_close_at = started_at + 12 hours
```

Фоновый воркер проверяет открытые смены не реже одного раза в минуту.

Если текущее время достигает `auto_close_at`:

1. Смена переводится в статус `auto_closed`.
2. Проставляется `ended_at = auto_close_at`.
3. Рассчитываются `duration_minutes`, `base_minutes`, `overtime_minutes`.
4. Создается уведомление оператору.
5. Создается запись в аудите.
6. При активной клиентской сессии оператор получает событие через Socket.IO.

### 12.16. Предупреждения о лимите смены

Оператор получает уведомления:

- за 30 минут до автозакрытия;
- за 20 минут до автозакрытия;
- за 10 минут до автозакрытия.

Пример для смены, начатой в 08:00:

| Уведомление | Время |
|---|---|
| За 30 минут | 19:30 |
| За 20 минут | 19:40 |
| За 10 минут | 19:50 |
| Автозакрытие | 20:00 |

Если пользователь не находится в активной сессии, уведомление сохраняется и отображается при следующем входе.

## 13. Управление конструкторской документацией и файловый обмен с САПР «Базис-Мебельщик»

### 13.1. Способ интеграции

Интеграция выполняется через файловый обмен.

Технолог выгружает файлы в сетевую директорию.

Для каждого заказа создается отдельная папка с идентификатором заказа.

### 13.2. Структура директории

```text
{share_root}/
  {orderExternalId}/
    v1/
      MATERIAL_SPEC.pdf
      EDGE_SPEC.pdf
      DRAWINGS.pdf
      SAW_PROGRAM.xml
      DRILL_PROGRAM_001.xml
      DRILL_PROGRAM_002.xml
      MILLING_PROGRAM.tcn
    v2/
      ...
```

### 13.3. Утвержденные имена файлов

| Тип документа | Имя файла | Расширение |
|---|---|---|
| Спецификация материалов | `MATERIAL_SPEC.pdf` | `.pdf` |
| Спецификация кромления | `EDGE_SPEC.pdf` | `.pdf` |
| Чертежи | `DRAWINGS.pdf` | `.pdf` |
| Программа раскроя | `SAW_PROGRAM.xml` | `.xml` |
| Программа сверления | `DRILL_PROGRAM_XXX.xml` | `.xml` |
| Программа фрезерной обработки | `MILLING_PROGRAM.tcn` или `MILLING_PROGRAM_XXX.tcn` | `.tcn` |

Где `XXX` — порядковый номер или идентификатор детали.

Если программ несколько, используется нумерация:

```text
DRILL_PROGRAM_001.xml
DRILL_PROGRAM_002.xml
DRILL_PROGRAM_003.xml
```

Если фрезерных программ несколько, допускается:

```text
MILLING_PROGRAM_001.tcn
MILLING_PROGRAM_002.tcn
```

Регистр расширений может игнорироваться, но имена файлов должны соответствовать шаблону.

### 13.4. Форматы управляющих программ

| Оборудование | Модуль Базис | Формат |
|---|---|---|
| Пильный центр с ЧПУ KDT KS-832H | БАЗИС-Раскрой | `.xml` |
| Сверлильно-присадочный центр с ЧПУ KDT KD-510H | БАЗИС-Мебельщик / карты присадки | `.xml` на деталь |
| Фрезерный обрабатывающий центр с ЧПУ KDT KN-2710L | БАЗИС-ЧПУ | `.tcn` |

### 13.5. Матрица обязательности документов

Безусловно обязательными считаются:

| Тип | Файл | Обязателен |
|---|---|---|
| Спецификация материалов | `MATERIAL_SPEC.pdf` | Да |
| Спецификация кромления | `EDGE_SPEC.pdf` | Да |
| Чертежи | `DRAWINGS.pdf` | Да |

Управляющие программы считаются обязательными при наличии соответствующих операций:

| Операция | Файл | Обязателен |
|---|---|---|
| Раскрой | `SAW_PROGRAM.xml` | Если в заказе есть раскрой |
| Сверление | `DRILL_PROGRAM_*.xml` | Если в заказе есть присадка |
| Фрезерная обработка | `MILLING_PROGRAM.tcn` или `MILLING_PROGRAM_*.tcn` | Если в заказе есть фрезерная обработка |

Матрица обязательности настраивается администратором.

### 13.6. Логика обработки файлов

`FileIngestWorker` выполняет:

1. Сканирование сетевой директории.
2. Поиск заказа по имени папки.
3. Если заказ не найден — помещение файлов в карантин.
4. Расчет хэша файлов.
5. Исключение дублей по хэшу.
6. Проверку имени файла.
7. Проверку расширения файла.
8. Распознавание типа файла.
9. Создание или обновление пакета КД.
10. Привязку документов к заказу.
11. Создание новой версии при изменении файлов.
12. Запись событий в аудит.
13. Создание записей в `document_package_issues` при ошибках.
14. Уведомление технолога о некорректных файлах.

### 13.7. Карантин файлов

Файл попадает в карантин, если:

- заказ не найден;
- имя файла не соответствует шаблону;
- расширение недопустимо или неизвестно;
- файл пустой;
- файл поврежден;
- тип файла не может быть достоверно определен.

Файл в карантине:

- не привязывается к пакету КД как валидный документ;
- сохраняется в изолированном состоянии;
- отображается в списке проблем;
- требует ручной проверки технологом.

Технолог получает уведомление о каждом файле, помещенном в карантин.

После ручной проверки файл может быть:

- подтвержден и привязан к пакету;
- отклонен;
- запрошен повторно у технолога.

### 13.8. Комплектность КД

Перед передачей КД в цех система проверяет комплектность.

Если пакет неполный, передача блокируется либо выполняется с явным подтверждением и указанием причины, если это разрешено настройками.

Статусы пакета:

- `draft`;
- `incomplete`;
- `ready`;
- `transferred`;
- `in_work`;
- `completed`;
- `archived`.

### 13.9. Печать документов

Пользователи должны иметь возможность:

- открыть документ;
- просмотреть документ;
- вывести документ на печать средствами браузера.

Для этикеток и печатных форм, сформированных в САПР «Базис-Мебельщик», поддерживается просмотр и печать без редактирования.

## 14. Интеграция с 1С:Комплексная автоматизация

### 14.1. Исходные условия интеграции

1. Доработку 1С:КА со стороны заказчика выполняет программист компании-дистрибьютора продуктов 1С.
2. Механизм OData доступен.
3. Публикация HTTP-сервисов возможна.
4. Тестовая база 1С предоставляется для разработки и тестирования интеграции.
5. Все поля производственного заказа обязательны для передачи.
6. Поступление материалов фиксируется в 1С специалистом снабжения.

### 14.2. Принципы интеграции

1. 1С:КА является источником правды для заказов, номенклатуры, остатков, закупок и бухгалтерии.
2. MES является источником правды для фактического хода производства.
3. Обмен выполняется не реже одного раза в 15 минут либо по событию.
4. Все сообщения должны быть идемпотентными.
5. Ошибки интеграции должны повторяться автоматически.
6. Интеграционные события должны быть видимы администратору.
7. Конкретные имена объектов 1С, полей и регистров выносятся в конфигурацию и маппинги.
8. До финального согласования 1С-структур разработка ведется с тестовыми фикстурами и mock-сервером.

### 14.3. Данные, получаемые из 1С

- производственные заказы со статусом «К производству»;
- клиенты;
- справочник номенклатуры;
- остатки материалов;
- поступления материалов;
- идентификатор сделки в amoCRM, если он передается из 1С.

### 14.4. Данные, передаваемые в 1С

- заказ переведен в статус «В производстве»;
- факт списания материалов;
- факт выпуска готовой продукции;
- данные о браке;
- заказ переведен в статус «Выполнен»;
- запрос распределения материала или фиксация дефицита;
- отчет по отработанным часам пользователей.

### 14.5. Механизм обмена

Используется гибридная схема:

1. **OData**  
   Для справочников, остатков, поступлений и периодического получения данных.

2. **Событийные HTTP-сервисы 1С**  
   Для бизнес-операций: статусы, списание, выпуск, брак, отчет по часам.

3. **Периодический опрос**  
   Как резервный механизм, чтобы не потерять события.

### 14.15. Маппинг пользователей и сотрудников 1С

Для экспорта отработанных часов каждый пользователь MES должен быть связан с сотрудником в 1С.

Связь хранится в поле:

```text
users.external_1c_employee_id
```

Если пользователь не связан с сотрудником в 1С:

- экспорт по такому пользователю помечается как проблемный;
- администратор получает уведомление;
- отчет продолжает формироваться по остальным пользователям.

### 14.16. Маппинг статусов

| Статус в 1С | Действие | Статус в MES |
|---|---|---|
| Черновик | Не передаем | Нет |
| В расчете | Не передаем | Нет |
| Согласование цены | Не передаем | Нет |
| Отменен | Передаем, если заказ уже был в MES | `canceled` |
| К производству | Создаем заказ в MES | `new`, далее по состоянию |
| В производстве | Устанавливает MES | `in_production` |
| Выполнен | Устанавливает MES после завершения всех партий | `completed` |

### 14.17. Требования к надежности интеграции

- Каждое входящее сообщение сохраняется в `integration_inbox`.
- Повторная доставка с тем же `messageId` не должна создавать дубли.
- Каждое исходящее событие сохраняется в `integration_outbox` в одной транзакции с бизнес-операцией.
- Повторные отправки выполняются с экспоненциальной задержкой.
- После превышения лимита попыток событие переводится в статус `dead_letter`.
- Администратор видит ошибки интеграции и может повторить отправку вручную.

### 14.18. Конфигурируемые маппинги

Интеграция с 1С реализуется через таблицу `integration_mappings` и настройки окружения.

Это позволяет изменять:

- имена объектов 1С;
- имена полей;
- коды статусов;
- единицы измерения;
- идентификаторы сотрудников;
- типы материалов;
- типы документов.

Изменение маппингов не должно требовать изменения программного кода, если структура данных не меняется концептуально.

### 18.6. Работа с API

- HTTP-клиент: Axios.
- Access token передается в заголовке `Authorization`.
- Refresh token обновляется через `/api/v1/auth/refresh`.
- При ошибке 401 выполняется попытка обновления токена.
- При ошибке 403 показывается сообщение о недостатке прав.
- При ошибке 409 показывается конфликт состояния.
- Для изменяющих операций передается `Idempotency-Key`.

### 18.7. Работа с Socket.IO

- Клиент подключается после авторизации.
- При отключении выполняется автоматическое переподключение.
- После переподключения запрашивается новый снапшот.
- События дашборда инвалидируют соответствующие запросы TanStack Query.
- Если пользователь не имеет права `dashboard.read`, подключение не выполняется.

### 18.8. Формы и валидация

- Валидация выполняется через Zod.
- Общие схемы валидации размещаются в `packages/validation`.
- Сообщения валидации только на русском языке.

## 19. Аналитический дашборд

### 19.1. Общие требования

Дашборд:

- доступен всем ролям, кроме бухгалтера;
- доступен по выделенному URL;
- является интерфейсом только для чтения;
- отображает данные в реальном времени;
- имеет одинаковый состав данных для всех ролей;
- не отображает файлы КД;
- не отображает финансовые данные.

### 19.2. Блоки дашборда

1. Сводная статистика за текущую смену.
2. Список активных производственных заказов.
3. Карточка производственного заказа.
4. Индикаторы отклонения от плана.
5. Текущие операционные зоны.
6. Загрузка станочного парка.
7. Брак по заказам.
8. Заказы, ожидающие материалы.
9. Дефицит материалов.
10. Время простоя.
11. История изменения статусов.
12. Фильтры и сортировка.

### 19.3. Сводная статистика

Показатели:

- заказы в работе;
- заказы, ожидающие материалы;
- общий процент выполнения;
- деталей произведено за смену;
- деталей в браке за смену;
- станков в работе;
- станков в простое;
- станков на обслуживании.

### 19.4. Карточка заказа

Карточка заказа должна отображать:

- идентификатор заказа;
- клиента;
- статус;
- фактическое начало;
- плановый срок окончания;
- прогнозируемый срок окончания;
- индикатор отклонения;
- количество плит ЛДСП;
- метры кромки;
- количество отверстий;
- готовые детали на складе;
- детали в производстве;
- текущую зону;
- текущую партию;
- общее количество партий;
- прогресс;
- брак в штуках;
- брак в процентах;
- дефицит материалов, если он есть.

### 19.5. Блок ожидающих материалов

Блок должен показывать:

- идентификатор заказа;
- клиента;
- дату перевода заказа в статус «К производству»;
- количество дней ожидания;
- перечень материалов;
- требуемое количество;
- поступившее количество;
- доступное количество;
- выданное в цех количество;
- остаток потребности;
- признак частичного поступления;
- признак дефицита.

Блок должен быть визуально выделен.

### 19.6. Фильтры

Дашборд поддерживает фильтрацию по:

- статусу заказа;
- текущей операционной зоне;
- клиенту;
- наличию отклонения от плана;
- уровню брака;
- наличию дефицита материалов.

### 19.7. Сортировка

Дашборд поддерживает сортировку по:

- дате начала;
- дате окончания;
- степени выполнения;
- уровню отклонения;
- уровню брака.

### 19.8. Обновление данных

- Основное обновление — через Socket.IO.
- Резервное обновление — периодический запрос дельты или снапшота.
- Время обновления не должно превышать 5 секунд с момента события.

## 20. Офлайн-режим цеховых терминалов

### 20.1. Требования

Терминалы в цеху должны сохранять работоспособность при кратковременной потере связи.

### 20.2. Что поддерживается офлайн

- просмотр текущего задания;
- просмотр КД по заданию, если файлы были закэшированы;
- отметка начала операции;
- отметка завершения операции;
- фиксация брака;
- фиксация простоя;
- отметка прерывания рабочей смены.

### 20.3. Что не поддерживается офлайн

- администрирование;
- управление ролями;
- передача КД в цех;
- изменение настроек;
- создание партий;
- распределение материалов;
- сложные мастерские операции, требующие актуального состояния других пользователей.

### 20.4. Механизм синхронизации

1. Клиент сохраняет операцию в локальную очередь в IndexedDB.
2. Каждой операции присваивается `idempotencyKey`.
3. При восстановлении связи клиент отправляет операции последовательно.
4. Сервер обрабатывает идемпотентные ключи.
5. При конфликте клиент показывает пользователю сообщение.
6. После успешной синхронизации операция удаляется из очереди.

### 20.5. Конфликты

Пример конфликта:

- оператор завершил партию офлайн;
- мастер уже завершил партию с другого терминала;
- при синхронизации сервер возвращает ошибку `CONFLICT`;
- клиент показывает актуальное состояние задания.

## 21. Требования к безопасности

### 21.1. Аутентификация

- вход по логину и паролю;
- пароли хранятся в виде хэша;
- рекомендуемый алгоритм хэширования: Argon2id или bcrypt;
- access token короткоживущий;
- refresh token подлежит отзыву при выходе;
- рекомендуется хранение refresh token в HttpOnly cookie либо ином защищенном механизме, согласованном с инфраструктурой.

### 21.2. Авторизация

- каждое защищенное действие проверяет право;
- проверка выполняется на сервере;
- интерфейс скрывает недоступные действия, но не заменяет серверную проверку;
- дашборд не дает доступа к мутациям.

### 21.3. Транспорт

- весь трафик по HTTPS;
- WebSocket через WSS;
- CORS ограничен разрешенными доменами;
- включаются стандартные защитные заголовки.

### 21.4. Аудит

Логируются:

- вход и выход;
- изменение заказов;
- создание партий;
- распределение материалов;
- передача КД;
- складские перемещения;
- операции цеха;
- регистрация брака;
- регистрация простоев;
- начало и завершение рабочих смен;
- корректировка смен;
- административные действия;
- интеграционные события.

### 21.5. Файлы

- файлы КД доступны только авторизованным пользователям;
- прямой публичный доступ к файлам исключается;
- доступ к файлу проверяется по правам и связи с заказом или заданием;
- карантинные файлы доступны только пользователям с правом просмотра и обработки карантина.

## 22. Инфраструктура, развертывание и резервное копирование

### 22.1. Среда развертывания

Система развертывается в облачной инфраструктуре.

Используется Docker.

Минимальный production-состав:

```text
nginx
api
worker
postgres
redis
file-storage
```

### 22.2. TLS

Принимаем следующий профиль:

1. Только TLS 1.2 и TLS 1.3.
2. Приоритет TLS 1.3.
3. HTTP автоматически перенаправляется на HTTPS.
4. WebSocket работает только через WSS.
5. Включить HSTS.
6. Сертификат:
   - Let's Encrypt, если используется публичный домен;
   - корпоративный сертификат, если система доступна только во внутренней сети;
   - коммерческий сертификат, если этого требует политика заказчика.
7. Автоматическое продление сертификата обязательно.

### 22.3. Сетевая интеграция с 1С

Для обмена с 1С предпочтительно использовать:

- site-to-site VPN;
- выделенный приватный канал;
- либо защищенный HTTPS с ограничением по IP и отдельным интеграционным пользователем.

### 22.4. Резервное копирование

- резервное копирование базы данных выполняется не реже одного раза в сутки;
- резервные копии хранятся отдельно от рабочего сервера;
- восстановление из резервной копии проверяется регулярно;
- файловое хранилище КД также включается в резервное копирование.

6. Технолог получает уведомление о карантине.
7. Технолог проверяет комплектность и передает КД в цех.
8. Мастер смены создает партию вручную.
9. Мастер распределяет материал.
10. При превышении остатка фиксируется дефицит.
11. Кладовщик перемещает материал в цех.
12. Материал поступает частично, мастер получает уведомление.
13. Мастер запрашивает повторное перемещение материала.
14. Заказ запускается при частичном поступлении материалов.
15. Оператор входит в систему, смена открывается автоматически.
16. Оператор прерывает смену по форс-мажорной причине.
17. Оператор продолжает прерванную смену.
18. Система показывает предупреждение за 30 минут до автозакрытия.
19. Система показывает предупреждение за 20 минут до автозакрытия.
20. Система показывает предупреждение за 10 минут до автозакрытия.
21. Система автоматически закрывает смену через 12 часов.
22. Отчет по часам корректно считает базовые и дополнительные часы.
23. Экспорт часов в 1С проходит по пользователям с заполненным `external_1c_employee_id`.
24. Экспорт часов показывает ошибку по пользователям без маппинга в 1С.
25. Оператор выполняет операцию.
26. Фиксируется брак.
27. Система учитывает, что брак требует замены.
28. Фиксируется простой.
29. Готовые детали перемещаются на склад.
30. Заказ завершается только после полного количества годных деталей.
31. В 1С отправляются статусы, списание и выпуск.
32. Дашборд обновляется в реальном времени.
33. Пользователь без прав не получает доступ к модулю.
34. Терминал цеха работает при кратковременной потере связи.
35. Повторная отправка интеграционного события не создает дублей.
