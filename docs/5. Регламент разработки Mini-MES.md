# 5. Учебный проект «Mini-MES» — дизайн и регламент командной разработки

> Тип документа: внутренний командный документ (регламент).
> Отношение к другим документам: документы 1–3 — «входящая» документация
> реального проекта (легенда), документ 4 — постановка учебной цели.
> Настоящий документ — принятый командой дизайн реализации и процесс разработки.

## 1. Идея проекта

1.1. Цель (из документа 4): получить реальный практический опыт использования
всего frontend-стека, необходимый для успешного технического собеседования.

1.2. Решение: учебный проект «Mini-MES» — уменьшенная копия MES-системы
(«стенд завода»): все механизмы стека работают вместе, но масштаб сокращён
до 3–4 бизнес-сущностей (заказ, партия, станок, задание), ~13 REST-эндпоинтов
и ~6 socket-событий.

1.3. Принципы:

- глубина важнее широты: лучше идеально понимать 10 мест применения
  технологии, чем поверхностно «пройти» всё;
- каждая строка кода должна быть объяснима вслух (пункт DoD);
- процесс разработки имитирует реальную команду: доска, спринты, ветки,
  pull request, код-ревью.

  1.4. Позиционирование на собеседовании: Mini-MES ведётся на отдельном
  GitHub-аккаунте и подаётся как pet-project: «код рабочего проекта приватный
  и принадлежит компании; для тренировки я сделал собственный учебный проект
  в знакомой предметной области». Личный аккаунт не связывается с учебным.

## 3. Бэкенд: сервер-имитатор `apps/mock-api`

3.1. Обоснование: в команде легенды backend пишут два других разработчика;
фронтендер интегрируется по спецификации контрактов (разделы 15 и 17
документа 3). В учебном проекте их роль играет мок-сервер. Разработка
«по контракту против мока, а затем переключение на реальный API» —
стандартная реальная практика. NestJS/PostgreSQL/Prisma/интеграции
не разрабатываются — это вне зоны ответственности фронтенда.

3.2. Реализация: Node.js + Express + Socket.IO; данные — массивы
в оперативной памяти (users, orders, batches, machines, shopTasks,
movements, defects); таймер-«симулятор цеха» (~10 с) изменяет состояние
и рассылает события — дашборд «живёт» без действий пользователя.

3.3. Контракты (копируют формат документа 3):

- базовый путь `/api/v1`, даты ISO 8601 UTC;
- формат списка — §15.2 (`items/page/pageSize/totalItems`);
- формат ошибки — §15.3 (`timestamp/errorCode/message`);
- `Idempotency-Key` для мутаций — §15.1; повтор с тем же ключом возвращает
  тот же ответ; конфликт ключей — `IDEMPOTENCY_CONFLICT`;
- конфликты состояния — 409 (`TASK_ALREADY_COMPLETED` и др.).

  3.4. Авторизация: `login/refresh/me/logout`; токены — непрозрачные
  случайные строки (в реальном бэкенде — JWT, фронтенду разница незаметна);
  access-токен живёт 2 минуты — для тренировки механики 401 → refresh.

  3.5. Эндпоинты мока:

| Метод и путь                                  | Назначение                            |
| --------------------------------------------- | ------------------------------------- |
| POST /api/v1/auth/login                       | Вход → токены                         |
| POST /api/v1/auth/refresh                     | Обновление access-токена              |
| GET /api/v1/auth/me                           | Текущий пользователь и роль           |
| POST /api/v1/auth/logout                      | Выход                                 |
| GET /api/v1/dashboard/summary                 | Сводная статистика                    |
| GET /api/v1/dashboard/orders                  | Карточки заказов (пагинация, фильтры) |
| GET /api/v1/dashboard/machines                | Панель станков                        |
| GET /api/v1/orders/:id/timeline               | Таймлайн заказа                       |
| POST /api/v1/shop/tasks/:id/start             | Начать операцию                       |
| POST /api/v1/shop/tasks/:id/complete          | Завершить операцию (Idempotency-Key)  |
| POST /api/v1/defects                          | Фиксация брака                        |
| POST /api/v1/warehouse/movements/:id/complete | Подтвердить перемещение               |
| GET /api/v1/notifications                     | Уведомления                           |

3.6. События Socket.IO (формат §17.2: `eventId/eventType/occurredAt/payload`):

| Событие                    | Назначение                           |
| -------------------------- | ------------------------------------ |
| dashboard.initial.snapshot | Снапшот при подключении и реконнекте |
| dashboard.summary.updated  | Изменилась сводная статистика        |
| dashboard.order.updated    | Изменилась карточка заказа           |
| dashboard.machine.updated  | Изменился статус станка              |
| dashboard.defect.created   | Зафиксирован брак                    |
| notification.created       | Новое уведомление                    |

## 5. Командный процесс

5.1. Роли:

- Разработчик (Middle Frontend) — пишет код, ведёт доску, открывает PR,
  мерджит после одобрения.
- Техлид/ментор (AI) — проектирование, разбор, код-ревью. Доступа к GitHub
  не имеет; ревью проходит в чате по diff (см. 5.4).

  5.2. Доска (GitHub Projects, Scrumban): колонки
  `Backlog → Спринт → В работе → Ревью → Готово`.

- Планирование спринта: перенос тасков Backlog → Спринт + оценка в часах
  (поле Estimate), спринт указывается полем Sprint.
- WIP-лимит колонки «В работе» = 1.
- Автоматизация: merge PR → таск в «Готово».
- Ретроспектива в конце спринта: что тормозило, что изменить.

  5.3. Definition of Done (все пункты обязательны):

1. код запускается и делает заявленное;
2. закоммичен в ветке задачи, линтеры проходят;
3. разработчик может объяснить каждую строку;
4. техлид выдал APPROVED в чате.

5.4. Git-регламент (GitHub Flow):

- Единственная долгоживущая ветка — `main` (защищена: только через PR,
  approvals 0, merge только squash, block force pushes, restrict deletions).
- Единственный прямой коммит в main в истории проекта — initial commit;
  всё далее — только через PR.
- Ветки: `<type>/MM-<номер>-<описание-kebab-case>`,
  type ∈ {feat, fix, chore, docs, refactor, test}.
- Коммиты (Conventional Commits): `<type>(<scope>): <описание> (MM-XXX)`,
  scope ∈ {root, web, api, ui, contracts, validation}; императив,
  с маленькой буквы, без точки, ≤ 72 символов; один коммит — одно изменение.
- Лейбл таска = type работы по нему.
- PR: название в формате коммита; в описании `Closes #N`; чек-лист DoD
  подставляется из `.github/pull_request_template.md`.

  5.5. Цикл ревью (пошагово):

```
GitHub                                    Чат
──────                                    ───
1. Таск из «Спринт» → «В работе»
2. git checkout main && git pull
3. git checkout -b <ветка>
4. Код → коммиты → push -u
5. Открыт PR (НЕ мерджим!) ─────────┐
                                    └──► 6. git diff main...HEAD → вставить в чат
                                         7. Ревью техлида:
                                            🔴 Critical / 🟡 Major /
                                            🔵 Minor / ❓ вопрос
                                         8. Правки в той же ветке,
                                            при необходимости — новый diff
                                         9. Вердикт APPROVED
10. Squash and merge на GitHub ◄─────────┘
    (таск → «Готово», ветка удалена)
11. Локально: checkout main, pull, удалить ветку
```

Примечания:

- PR на GitHub — «журнал» процесса (защита main, чек-лист, история,
  автоматизация доски); фактическое чтение кода происходит в чате:
  diff в чате — то же содержимое, что вкладка «Files changed» PR.
- Правки после ревью коммитятся в ту же ветку; при squash-merge они
  сожмутся в один коммит, переписывать историю не нужно.

  5.6. Организация чатов с техлидом:

- Чат «Начало» — стратегия, планирование, изменение настоящего регламента.
- На каждый таск — отдельный чат с именем «MM-XXX · <название>»;
  в нём — вопросы реализации и ревью diff этого таска.
- Документы 1–5, прикреплённые к проекту, доступны во всех чатах.
- Если для ревью нужен код из закрытых тасков — вставлять фрагмент в чат.
