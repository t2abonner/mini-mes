# Система оперативного управления производственными процессами (MES)

## 1. Общие сведения

### 1.1. Полное наименование системы

Система оперативного управления производственными процессами мебельного предприятия (далее — Система, MES-система).

### 1.2. Условное обозначение

MES-MF (Manufacturing Execution System for Manufacturing Furniture parts).

### 1.3. Назначение системы

Система предназначена для автоматизации оперативного управления производственными процессами на уровне цеха (Уровень 3 по стандарту IEC 62264), обеспечения прослеживаемости незавершенного производства в реальном времени, предоставления единой аналитической панели мониторинга для всех участников процесса и интеграции с существующими корпоративными информационными системами заказчика.

### 1.4. Границы системы

Система покрывает производственный участок от момента передачи полного пакета конструкторской документации технологом в цех до момента перемещения готовых деталей на склад готовой продукции.

Функции, находящиеся вне зоны ответственности данной Системы:

- Прием заказов и коммуникация с клиентами — осуществляется в amoCRM.
- Бухгалтерский учет, взаиморасчеты с контрагентами, выставление счетов — осуществляется в 1С:Комплексная автоматизация.
- Предварительный расчет стоимости заказа — осуществляется в связке САПР «Базис-Мебельщик» и 1С:Комплексная автоматизация.
- Закупка материалов у поставщиков — осуществляется в 1С:Комплексная автоматизация.
- Складской учет материалов и готовой продукции в количественно-суммовом выражении — осуществляется в 1С:Комплексная автоматизация.

## 2. Назначение и цели создания системы

### 2.1. Назначение

Система обеспечивает оперативное управление производственным процессом после того, как заказ согласован клиентом, материалы зарезервированы или закуплены, а технолог подготовил полный пакет конструкторской документации.

Система обеспечивает:

- Прием полного пакета конструкторской документации от технолога и привязку его к производственному заказу.
- Формирование сменных заданий для цеха на основании полученной документации.
- Отслеживание перемещения материалов и полуфабрикатов между операционными зонами цеха в режиме реального времени.
- Фиксацию факта выполнения операций, учета брака и простоя оборудования.
- Управление внутрискладскими перемещениями (материал в цех, готовые детали из цеха на склад).
- Передачу данных о фактическом расходе материалов и выпуске готовой продукции в 1С:Комплексная автоматизация.
- Предоставление единой аналитической панели мониторинга состояния производственных процессов для всех участников.

### 2.2. Цели создания системы

| Цель | Ожидаемый результат |
|---|---|
| Исключение рассинхронизации между цехом и складом | Все участники видят актуальный статус перемещения материалов и полуфабрикатов в режиме реального времени |
| Исключение бумажного документооборота в цеху | Операторы получают чертежи и управляющие программы через терминалы Системы |
| Прозрачность незавершенного производства | Точное знание местоположения каждой партии деталей на любом этапе обработки |
| Интеграция с существующим ИТ-ландшафтом | Бесшовный обмен данными с 1С:КА без ручного дублирования |
| Обеспечение технолога обратной связью | Технолог видит, какие документы переданы в цех и по каким заказам начато производство |
| Единая точка получения информации о состоянии производства | Любая роль может в любой момент открыть аналитический дашборд и узнать текущий статус любого заказа без обращения к другим сотрудникам |
| Раннее выявление отклонений от плана | Индикатор отклонения позволяет менеджеру заранее предупредить клиента о задержке |
| Оперативное выявление узких мест в производстве | Визуализация загрузки станков и текущих операционных зон позволяет мастеру смены перераспределять ресурсы |
| Контроль качества в реальном времени | Отображение количества брака по каждому заказу позволяет оперативно реагировать на систематические проблемы |

## 3. Характеристика объекта автоматизации

### 3.1. Описание предприятия

Производственное предприятие среднего масштаба, расположенное в региональном центре. Компания специализируется на изготовлении деталей корпусной мебели в качестве подрядчика для производителей корпусной мебели. Предприятие самостоятельно не производит конечные мебельные изделия, а лиш предоставляет B2B услугу изготовления деталей корпусной мебели.

### 3.5. Модель ценообразования (вне зоны ответственности MES, описана для контекста)

Расчет стоимости для клиента выполняется в два прохода.

**Первый проход (предварительный расчет):**

1. Менеджер получает от заказчика файл модели в формате .b3d (формат САПР «Базис-Мебельщик»).
2. Менеджер передает файл технологу для предварительного быстрого расчета.
3. Технолог выполняет базовый анализ в «Базис-Мебельщик»: раскрой плит, подсчет метража кромки, количество отверстий.
4. «Базис-Мебельщик» выгружает спецификацию материалов и трудоемкость в формате XML.
5. На этом этапе чертежи для ЧПУ и полный пакет документации не формируются.
6. Спецификация загружается в 1С:КА.
7. 1С:КА автоматически рассчитывает себестоимость по заранее сформированному прайс-листу на услуги:
   - Распил ЛДСП: X рублей за квадратный метр.
   - Присадка: Y рублей за отверстие.
   - Кромление: Z рублей за погонный метр.
8. Прайс-лист формируется и поддерживается бухгалтером и коммерческим директором.
9. 1С:КА умножает количество операций из спецификации на ставки из справочника «Виды работ» и передает расчетную стоимость в amoCRM.
10. Менеджер видит в amoCRM расчетную стоимость, добавляет маржу и отправляет коммерческое предложение заказчику.

**Второй проход (полный пакет документации):**

1. Заказчик согласует цену и подписывает договор (или оплачивает аванс).
2. Менеджер меняет статус сделки в amoCRM на «Согласовано».
3. Сигнал уходит в 1С:КА, заказ переводится в статус «К производству».
4. Технолог возвращается к модели и формирует полный пакет конструкторской документации:
   - Управляющие программы для станков с ЧПУ.
   - Чертежи деталей.
   - Карты раскроя.
   - Карты присадки.
   - Спецификации материалов для цеха.
   - Все документы в формате PDF для работников цеха.
5. Полный пакет КД передается в MES-систему.
6. MES-система запускает производственный процесс.

### 3.6. Статусная модель заказов в 1С:Комплексная автоматизация

| Статус заказа в 1С:КА | Описание | Кто переводит |
|---|---|---|
| Черновик | Получен файл .b3d от заказчика | Менеджер (через интеграцию с amoCRM) |
| В расчете | Файл передан технологу для предварительного расчета | Менеджер |
| Согласование цены | Технолог выполнил расчет, стоимость передана менеджеру | 1С:КА (автоматически) |
| Отменен | Заказчик отказался, спецификация архивируется | Менеджер |
| К производству | Заказчик согласовал цену и подписал договор | 1С:КА (по сигналу из amoCRM) |
| В производстве | Заказ запущен в MES-систему | MES-система |
| Выполнен | Все детали произведены и приняты на склад | 1С:КА (по сигналу из MES) |

Ограничение прав доступа: Специалист снабжения видит в списке заказов только те, у которых статус «К производству» или выше. Он физически не может заказать материалы по заказу со статусом «Согласование цены».

Резервирование: Когда заказ переходит в статус «К производству», материалы автоматически резервируются на складе. Если их нет в наличии, формируется потребность в закупке.

### 3.8. Многопартийные заказы

Для заказов с большим объемом производства допускается разбивка на несколько последовательных партий. В этом случае производственный цикл повторяется для каждой партии:

1. Партия материала передается со склада в цех.
2. Партия обрабатывается в цеху через все операционные зоны.
3. Готовые детали партии передаются обратно на склад.
4. Заказ не считается выполненным до тех пор, пока не будут обработаны и переданы на склад все запланированные партии.
5. После завершения последней партии заказ переводится в статус «Выполнен».

## 4. Требования к MES системе

### 4.1. Требования к функциональным характеристикам MES системы

#### 4.1.1. Модуль «Прием и управление производственными заказами»

- Система должна получать из 1С:КА производственные заказы со статусом «К производству».
- При получении заказа Система должна автоматически создавать сущность «Производственный заказ» со следующими атрибутами:
  - Идентификатор заказа в 1С:КА.
  - Идентификатор сделки в amoCRM.
  - Идентификатор клиента.
  - Перечень требуемых деталей (номенклатура, количество, материал, размеры).
  - Плановая дата начала производства.
  - Плановая дата готовности.
  - Статус заказа.
- Система должна передавать в 1С:КА информацию о переводе заказа в статус «В производстве».
- Система должна передавать в 1С:КА информацию о переводе заказа в статус «Выполнен».
- Система должна предоставлять технологу интерфейс с возможностью просмотра списка производственных заказов и статуса переданной конструкторской документации для того или иного заказа, что дает технологу оперативное пониманеи для какго заказа он уже передал все необходимые документы для производства, а для какого еще нет.

#### 4.1.2. Модуль «Управление конструкторской документацией»

- Система должна принимать от технолога полный пакет файлов конструкторской документации:
  - Управляющие программы для пильных центров с ЧПУ KDT KS-832H.
  - Таблицы спецификаций для кромкооблицовочных станков KDT KE-710BT.
  - Карты сверления и управляющие программы для сверлильно-присадочных центров с ЧПУ KDT KD-510H.
  - Чертежи деталей и управляющие программы для фрезерного обрабатывающего центра с ЧПУ KDT KN-2710L.
  - Спецификации материалов для цеха.
  - Все документы в формате PDF для работников цеха.
- Система должна связывать пакет конструкторской документации с соответствующим производственным заказом.
- Система должна предоставлять технологу интерфейс для проверки полноты пакета документации перед передачей в цех и отслеживания статуса: «Передано в цех», «В работе», «Завершено».
- Система должна предоставлять мастеру смены и операторам доступ к актуальной версии конструкторской документации для конкретного задания.
- Система должна хранить историю версий конструкторской документации и фиксировать, какая версия была передана в цех.

#### 4.1.3. Модуль «Управление внутрискладскими перемещениями»

- Система должна формировать задание для кладовщиков на перемещение материала (ЛДСП плита) со склада в зону раскроя на основании производственного заказа.
- Система должна фиксировать факт перемещения материала кладовщиком.
- Система должна фиксировать факт перемещения полуфабрикатов между операционными зонами цеха.
- Система должна формировать задание для кладовщиков на перемещение готовых деталей из цеха на склад готовой продукции.
- Система должна фиксировать факт перемещения готовых деталей кладовщиком.
- Система должна предоставлять старшему кладовщику интерфейс для координации работы рядовых кладовщиков и контроля статуса всех перемещений.
- Система должна передавать в 1С:КА данные о фактическом расходе материалов со склада в производство и о выпуске готовой продукции на склад.
- Для многопартийных заказов Система должна отслеживать перемещения в разрезе каждой отдельной партии.

#### 4.1.4. Модуль «Управление цехом и сменными заданиями»

- Система должна формировать сменное задание для мастера смены на основании производственных заказов и конструкторской документации.
- Система должна предоставлять мастеру смены интерфейс (планшет или терминал в цеху) со следующими функциями:
  - Просмотр списка активных производственных заказов и их приоритетов.
  - Просмотр текущей загрузки каждой операционной зоны.
  - Отметка факта начала и завершения операции на конкретном станке.
  - Отметка факта перемещения партии деталей в следующую операционную зону.
  - Ввод информации о браке и причинах простоя.
  - Контроль своевременного технического обслуживания станков (замена режущего инструмента).
- Система должна предоставлять оператору станка интерфейс со следующими функциями:
  - Получение текущего задания для своего станка.
  - Доступ к актуальной управляющей программе и чертежам.
  - Отметка факта начала и завершения обработки партии.
  - Отметка факта обнаружения брака.

#### 4.1.5. Модуль «Интеграция с 1С:Комплексная автоматизация»

- Система должна обмениваться данными с 1С:Комплексная автоматизация через стандартные механизмы интеграции платформы 1С:Предприятие 8.3: REST API или OData.
- Система должна получать из 1С:КА следующие данные:
  - Производственные заказы со статусом «К производству».
  - Справочник номенклатуры материалов.
  - Текущие остатки материалов на складе.
- Система должна передавать в 1С:КА следующие данные:
  - Факт перевода заказа в статус «В производстве».
  - Факт списания материалов со склада в производство.
  - Факт выпуска готовой продукции на склад.
  - Данные о браке.
  - Факт перевода заказа в статус «Выполнен».
- Обмен данными должен происходить не реже одного раза в 15 минут или по событию (триггерная модель).

#### 4.1.6. Модуль «Интеграция с САПР «Базис-Мебельщик»

- Система должна принимать полный пакет конструкторской документации из САПР «Базис-Мебельщик».
- Интеграция должна осуществляться через файловый обмен, то есть выгрузка .pdf фалов и файлов программ для ЧПУ в специальную сетевую дерикторию, для каждого заказа создается отдельная дериктория, с именем в виде идетификатора заказа.
- Система должна автоматически распознавать тип файла (управляющая программа, чертеж, спецификация) и привязывать его к соответствующему производственному заказу.

#### 4.1.7. Модуль «Аналитический дашборд»

##### 4.1.7.1. Общие требования

- Система должна предоставлять единый аналитический дашборд, доступный всем ролям предприятия за исключением роли «Бухгалтер», но не потому что ему запрещено, а по тому что просто не нужно.
- Доступ к дашборду осуществляется по логину и паролю, так же как и к остальным модулям Системы.
- Дашборд является интерфейсом только для чтения. Ни одна роль не имеет возможности изменять данные или влиять на производственные процессы через дашборд.
- Дашборд отображает актуальное состояние производственных процессов в режиме реального времени.
- Дашборд должен быть доступен с любого клиентского терминала Системы (терминал в цеху, рабочее место технолога, рабочее место старшего кладовщика).
- Интерфейс дашборда одинаков для всех ролей и не зависит от уровня доступа пользователя.
- Дашборд должен поддерживать одновременное отображение информации по нескольким производственным заказам, если в цеху исполняется несколько заказов параллельно.
- Для многопартийных заказов дашборд должен отображать прогресс в разрезе каждой отдельной партии.

##### 4.1.7.2. Сводная статистика за период

Дашборд должен содержать блок сводной статистики, расположенный в верхней части интерфейса и отображающий агрегированные показатели за текущую смену:

| Показатель | Описание |
|---|---|
| Заказы в работе | Количество производственных заказов, находящихся в статусе «В производстве» |
| Заказы, ожидающие материалы | Количество заказов в статусе «К производству», для которых материалы еще не поступили на склад |
| Общий процент выполнения | Средневзвешенный процент выполнения всех активных заказов |
| Деталей произведено за смену | Общее количество деталей, обработанных и переданных на склад за текущую смену |
| Деталей в браке за смену | Общее количество забракованных деталей за текущую смену |
| Станков в работе | Количество станков, находящихся в активном состоянии |
| Станков в простое | Количество станков, находящихся в состоянии простоя |
| Станков на обслуживании | Количество станков, находящихся на плановом или внеплановом обслуживании |

##### 4.1.7.3. Карточка производственного заказа

Дашборд должен отображать список всех активных производственных заказов в виде таблицы или карточек. Для каждого заказа отображается следующая информация:

| Поле | Описание |
|---|---|
| Уникальный идентификатор заказа | Номер заказа, присвоенный при создании в 1С:КА |
| Идентификатор клиента | Наименование заказчика (производителя корпусной мебели) |
| Текущий статус заказа | Один из статусов: «Ожидание материалов», «В производстве», «Выполнен» |
| Срок начала исполнения | Дата и время фактического начала производственных процессов по данному заказу |
| Планируемый срок окончания | Дата и время планируемого завершения всех производственных процессов по данному заказу |
| Прогнозируемый срок окончания | Дата и время прогнозируемого завершения на основании текущей скорости обработки |
| Индикатор отклонения от плана | Визуальный индикатор, отображающий разницу между планируемым и прогнозируемым сроками окончания |
| Количество плит ЛДСП | Общее количество плит ЛДСП, необходимых для выполнения заказа |
| Количество погонных метров кромки | Общее количество погонных метров кромочного материала, необходимого для выполнения заказа |
| Количество отверстий присадки | Общее количество отверстий присадки, необходимых для выполнения заказа |
| Готовые детали на складе | Количество деталей данного заказа, которые уже произведены и переданы на склад готовой продукции |
| Детали в производстве | Количество деталей данного заказа, которые в данный момент находятся на одном из этапов обработки в цеху |
| Текущая операционная зона | Наименование операционной зоны, на которой в данный момент обрабатывается текущая партия: раскрой, кромление, сверление или фрезерная обработка |
| Текущая партия | Номер текущей партии (для многопартийных заказов) |
| Общее количество партий | Общее количество запланированных партий (для многопартийных заказов) |
| Прогресс выполнения | Визуальный индикатор степени выполнения заказа в процентах |
| Брак по заказу (абсолютное) | Количество забракованных деталей по данному заказу в абсолютном выражении |
| Брак по заказу (процент) | Количество забракованных деталей по данному заказу в процентах от общего объема |

##### 4.1.7.4. Индикатор отклонения от плана

- Для каждого производственного заказа Система должна рассчитывать прогнозируемый срок окончания на основании текущей скорости обработки деталей и оставшегося объема работ.
- Дашборд должен отображать разницу между планируемым сроком окончания и прогнозируемым сроком окончания.
- Если прогнозируемый срок окончания не превышает планируемый, индикатор отображается нейтральным цветом.
- Если прогнозируемый срок окончания превышает планируемый не более чем на заданный порог (настраиваемый параметр), индикатор отображается предупреждающим цветом.
- Если прогнозируемый срок окончания превышает планируемый более чем на заданный порог, индикатор отображается критическим цветом.
- Пороговые значения отклонения должны быть настраиваемыми администратором Системы.

##### 4.1.7.5. Текущая операционная зона

- Для каждого активного производственного заказа дашборд должен отображать, на каком именно этапе обработки находится текущая партия деталей.
- Возможные значения текущей операционной зоны:
  - Ожидание материалов.
  - Раскрой (пильные центры с ЧПУ KDT KS-832H).
  - Кромление (кромкооблицовочные станки KDT KE-710BT).
  - Сверление (сверлильно-присадочные центры с ЧПУ KDT KD-510H).
  - Фрезерная обработка (фрезерный обрабатывающий центр с ЧПУ KDT KN-2710L).
  - Перемещение на склад готовой продукции.
- Для многопартийных заказов текущая операционная зона отображается для каждой отдельной партии.

##### 4.1.7.6. Загрузка станочного парка

- Дашборд должен содержать блок, отображающий текущий статус каждого станка в цеху.
- Для каждого станка отображается следующая информация:
  - Наименование и модель станка.
  - Операционная зона.
  - Текущий статус: «Работает», «Простой», «Обслуживание».
  - Идентификатор производственного заказа, который в данный момент обрабатывается на данном станке (если станок в статусе «Работает»).
  - Идентификатор партии, которая в данный момент обрабатывается на данном станке (если станок в статусе «Работает»).
- Станки должны быть сгруппированы по операционным зонам.
- Статус станка должен обновляться в режиме реального времени на основании данных, вводимых операторами и мастером смены.

##### 4.1.7.7. Количество брака по заказу

- Для каждого активного производственного заказа дашборд должен отображать количество забракованных деталей.
- Количество брака отображается в абсолютном выражении (количество штук) и в процентном отношении к общему объему заказа.
- Система должна позволять фильтровать заказы по уровню брака для быстрого выявления заказов с повышенной долей брака.
- Данные о браке поступают в Систему от операторов станков и мастера смены в процессе выполнения операций.

##### 4.1.7.8. Ожидающие материалы

- Дашборд должен содержать блок, отображающий список заказов, находящихся в статусе «К производству», но материалы для которых еще не поступили на склад.
- Для каждого такого заказа отображается:
  - Идентификатор заказа.
  - Идентификатор клиента.
  - Дата перевода заказа в статус «К производству».
  - Количество дней ожидания материалов.
  - Перечень материалов, ожидаемых поступления.
- Блок должен быть визуально выделен для привлечения внимания специалиста снабжения и старшего кладовщика.

##### 4.1.7.9. Время простоя

- Дашборд должен отображать суммарное время простоя оборудования за текущую смену.
- Время простоя рассчитывается на основании данных, вводимых операторами и мастером смены при отметке факта простоя.
- Дашборд должен отображать время простоя как в разрезе каждого отдельного станка, так и суммарно по всему цеху.
- Для каждого станка отображается причина простоя, если она была указана оператором или мастером смены.
- Дашборд должен отображать историю простоев за выбранный период (текущая смена, текущий день, текущая неделя).

##### 4.1.7.10. История изменения статусов

- Дашборд должен предоставлять возможность раскрыть карточку производственного заказа и просмотреть хронологическую историю изменения его статусов.
- История должна содержать следующие события:
  - Дата и время перевода заказа в статус «К производству».
  - Дата и время поступления материалов на склад.
  - Дата и время передачи материалов в цех.
  - Дата и время начала обработки в каждой операционной зоне.
  - Дата и время завершения обработки в каждой операционной зоне.
  - Дата и время обнаружения брака (с указанием количества и операционной зоны).
  - Дата и время перемещения готовых деталей на склад.
  - Дата и время перевода заказа в статус «Выполнен».
- Для многопартийных заказов история отображается в разрезе каждой отдельной партии.
- История должна отображаться в виде временной шкалы (таймлайн) для наглядности.

##### 4.1.7.11. Требования к визуальному представлению и фильтрации

- Дашборд должен отображать список всех активных производственных заказов в виде таблицы или карточек.
- Дашборд должен поддерживать фильтрацию по следующим параметрам:
  - Статус заказа.
  - Текущая операционная зона.
  - Клиент.
  - Наличие отклонения от плана.
  - Уровень брака.
- Дашборд должен поддерживать сортировку по следующим параметрам:
  - Дата начала.
  - Дата окончания.
  - Степень выполнения.
  - Уровень отклонения от плана.
  - Уровень брака.
- Дашборд должен автоматически обновлять данные без необходимости ручного обновления страницы.
- Дашборд должен быть адаптирован для отображения на экранах различного размера (монитор рабочего места, планшет, промышленный терминал).

| Роль | Модуль «Заказы» | Модуль «КД» | Модуль «Склад» | Модуль «Цех» | Аналитический дашборд |
|---|---|---|---|---|---|
| Старший технолог | Просмотр | Загрузка, передача, просмотр | Нет | Нет | Да |
| Технолог | Просмотр | Загрузка, передача, просмотр | Нет | Нет | Да |
| Старший кладовщик | Просмотр | Нет | Управление, координация | Нет | Да |
| Кладовщик | Нет | Нет | Выполнение заданий | Нет | Да |
| Мастер смены | Просмотр | Просмотр | Нет | Управление | Да |

#### 4.2.2. Доступ к аналитическому дашборду

Аналитический дашборд доступен следующим ролям:

- Коммерческий директор.
- Менеджер.
- Старший технолог.
- Технолог.
- Специалист снабжения.
- Старший кладовщик.
- Кладовщик.
- Мастер смены.
- Оператор станка с ЧПУ.

Для всех перечисленных ролей дашборд предоставляет идентичный набор данных и функций. Дашборд является интерфейсом только для чтения и не предоставляет возможности изменять данные или влиять на производственные процессы.

#### 4.2.3. Роли без доступа к Системе

Следующие роли работают исключительно в 1С:Комплексная автоматизация и не имеют доступа к терминалам Системы:

- Бухгалтер.

#### 4.2.4. Добовление ролей в Системе

Система должа предостовлять возможность, добавить любую роль и назначать ей права. Функциональность добавления ролей и парв другим ролям, должна быть доступна только пдминистратору системы. Роль администратора системы по умолчинию добавленна только комерческому директору. 

### 4.3. Требования к архитектуре системы

- Система должна быть реализована в клиент-серверной архитектуре.
- Серверная часть (бэкенд) должна быть реализована в виде REST API.
- Клиентская часть (фронтенд) должна быть реализована в виде SPA веб-приложения.
- Аналитический дашборд должен быть реализован как отдельное представление внутри клиентского веб-приложения, доступное по выделенному URL-адресу.
- Система должна хранить данные в реляционной базе данных.
- Система должна поддерживать одновременную работу не менее 30 пользователей.
- Система должна быть рассчитана на работу в локальной сети предприятия или в облачной инфраструктуре по выбору заказчика.
- Обновление данных на аналитическом дашборде должно осуществляться с использованием технологии WebSocket для обеспечения обновления в режиме реального времени без ручного обновления страницы.
- Система должна хранить историю изменения статусов заказов и историю простоев оборудования не менее 12 месяцев.

### 4.4. Требования к надежности и безопасности

- Система должна обеспечивать резервное копирование базы данных не реже одного раза в сутки.
- Система должна логировать все действия пользователей с указанием роли, времени и измененных данных.
- Доступ к системе должен осуществляться по логину и паролю.
- Система должна быть устойчива к потере связи с сервером на клиентских терминалах в цеху с последующей синхронизацией данных при восстановлении соединения.
- Аналитический дашборд не должен предоставлять доступ к конструкторской документации, управляющим программам или финансовым данным. Дашборд отображает только агрегированную информацию о состоянии производственных процессов.

### 4.5. Требования к производительности

- Время отклика ролевых интерфейсов на действия пользователя не должно превышать 2 секунд.
- Время формирования сменного задания не должно превышать 5 секунд.
- Время загрузки аналитического дашборда не должно превышать 3 секунд при одновременном отображении не менее 20 активных производственных заказов.
- Время обновления данных на аналитическом дашборде не должно превышать 5 секунд с момента фиксации события в Системе.
- Система должна обрабатывать не менее 500 производственных заказов в месяц без деградации производительности.

## 6. Порядок контроля и приемки системы

- Приемка каждого этапа работ производится путем демонстрации функциональности заказчику.
- Критерием приемки является соответствие реализованной функциональности требованиям настоящего ТЗ и успешное прохождение приемо-сдаточных испытаний.
- Приемо-сдаточные испытания включают:
  - Проверку прохождения производственного заказа через все этапы от получения статуса «К производству» в 1С:КА до выпуска готовой продукции на склад.
  - Проверку корректности обмена данными с 1С:КА (статусы, списание, оприходование).
  - Проверку корректности приема конструкторской документации из САПР «Базис-Мебельщик».
  - Проверку работы всех ролевых интерфейсов.
  - Проверку работы аналитического дашборда:
    - Доступность для всех ролей (за исключением бухгалтера).
    - Корректность отображения сводной статистики за период.
    - Корректность отображения карточек заказов со всеми полями.
    - Корректность работы индикатора отклонения от плана.
    - Корректность отображения текущей операционной зоны для каждой партии.
    - Корректность отображения загрузки станочного парка.
    - Корректность отображения количества брака по заказу.
    - Корректность отображения заказов, ожидающих материалы.
    - Корректность отображения времени простоя.
    - Корректность отображения истории изменения статусов (таймлайн).
    - Обновление данных в реальном времени.
    - Корректность отображения многопартийных заказов.
    - Работа фильтров и сортировки.
  - Проверку сценария отказа: заказ не согласован, материалы не закупаются, в производство не попадает.
  - Проверку того, что дашборд не предоставляет возможности изменения данных.
- По результатам испытаний составляется акт приемки системы в промышленную эксплуатацию.
